# Source organization

The plugin uses a simple Feature First structure. Keep code close to the feature that owns it and introduce shared layers only after reuse is real.

## Plugin root

`app/` is the WordPress plugin root.

```text
app/
├── src/
│   └── <feature>/
├── build/              # generated, not committed
├── package.json
├── composer.json
└── yamabiko-blocks.php
```

The exact files inside a feature depend on the feature. Do not create a complete directory template in advance.

## Feature ownership

Place a feature's block metadata, editor code, styles, PHP integration, and focused tests together when they belong to the same behavior.

```text
src/
└── example/
    ├── block.json
    └── index.tsx
```

Use clear feature names. A directory should describe a product responsibility rather than a technical category.

## Shared code

Do not create generic `shared/`, `utils/`, or `helpers/` directories for possible future reuse.

Keep code inside its owning feature until at least two real features need the same behavior. When extracting shared code:

- give it a specific responsibility;
- keep its public surface small;
- avoid dependencies on one feature's internal details;
- update imports and tests as part of the same change.

Small duplication is preferable to an unclear abstraction.

## Entry files

Entry files should be thin. They may:

- import feature metadata and dependencies;
- register a block, format, plugin, or other WordPress integration;
- connect existing feature components.

Move substantial state management, transformations, and UI behavior into named modules within the feature.

## Tests

Keep focused tests close to the code they verify when a test framework is introduced for that code. Use a top-level test directory only for repository-wide, integration, or end-to-end behavior that does not belong to one feature.

Do not add empty test directories or describe test suites that are not currently available.

## Generated files

`app/build/` is generated by `npm run build` or `npm start`. Do not edit or commit it.

`node_modules/` and `vendor/` are installed dependencies and are also not committed. Lockfiles remain committed so installations are reproducible.

## Evolving the structure

Change the structure when current implementation pressure justifies it, not to anticipate unimplemented drag-and-drop, REST, HMR, distribution, or other systems. Document a new boundary when it becomes part of the actual codebase.
