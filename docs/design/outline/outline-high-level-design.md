## 2. 文書の目的

本書は、要件定義書で定義されたYamabiko OutlineのMVP要件を、Gutenbergブロックエディター上で実現するための基本設計を定める。

次の内容は要件定義書を正とし、本書では繰り返さない。

- 背景と解決する問題
- 対象ユーザーとユーザーストーリー
- 製品目標と非目標
- 成功指標
- リリース段階
- 製品上の仮説とリスク
- MVP受け入れ条件

本書は、システム構成、データ形式、処理方式、UI連携、エラー処理、非機能要件、テスト方針を扱う。

## 3. 設計原則

1. WordPress Data Storeのブロック状態を単一の正とする
2. Gutenberg標準のDocument Outlineを直接変更しない
3. 投稿内容やフロントエンド出力を変更しない
4. 公開APIを優先し、Gutenberg内部DOMへの依存を避ける
5. 取得できない見出しを推測しない
6. 出力HTMLを無条件に解析しない
7. 一部の解析やアダプターが失敗しても、取得済みのアウトラインを表示する
8. 表示、解析、診断、ナビゲーションの責務を分離する

## 4. UI設計

### 4.1 対応エディターと表示位置

初期バージョンでは、投稿および固定ページの投稿エディターだけを対象とする。

サイトエディター、ウィジェットエディター、カスタム投稿タイプ、およびその他の編集コンテキストにはサイドバーを登録しない。

対象のブロックエディター内に「文書構造」サイドバーを追加し、標準の投稿設定サイドバーとは独立したプラグインサイドバーとして実装する。

サイドバーは`@wordpress/plugins`の`registerPlugin`と`@wordpress/editor`の`PluginSidebar`で登録する。製品コードは独立したエディター用ビルドエントリーとし、PHPの`enqueue_block_editor_assets`で読み込む。

対象判定は`get_current_screen()`の公開情報を使用し、画面の`base`が`post`、かつ`post_type`が`post`または`page`の場合だけエントリーを読み込む。JavaScript側で非対象画面に登録した後で非表示にする方式は採用しない。

### 4.2 表示構成

```text
文書構造

H1 製品サイト
├─ H2 サービス
│  ├─ H3 サービスA
│  └─ H3 サービスB
├─ H2 導入事例
└─ H2 よくある質問

見出し診断
警告 1件

アウトラインが一部不完全な可能性があります
```

各アウトライン項目には、次を表示する。

- 見出しレベル
- 見出しテキスト
- 診断状態
- 移動可否

### 4.3 操作

- クリックまたはEnterキーで対象ブロックへ移動する
- 移動できない項目は表示を維持し、理由を示す
- 警告を色だけで表現しない
- フォーカス位置を視覚的に確認できるようにする

## 5. アウトライン生成

### 5.1 処理フロー

```text
WordPress Data Store
        ↓
ブロックツリー取得
        ↓
Standard Heading Resolver
＋ Outline Adapter Registry
＋ HTML Heading Parser
        ↓
OutlineNode一覧
        ↓
Outline Diagnostics
        ↓
Document Outline Sidebar
```

### 5.2 取得元

見出しは次から取得する。

1. 標準Headingブロック
2. innerBlocks内のHeadingブロック
3. 登録済みアダプター
4. 安全に解析できるHTMLブロックまたはClassicブロック
5. 展開済みブロックツリーから取得できる同期パターン内のHeadingブロック

各ブロックは、1つのResolver、アダプター、またはParserだけで処理する。

処理優先順位は次のとおりとする。

1. 組み込みResolver
2. 登録済みアダプター
3. HTML Heading Parser

同じブロックを複数の取得元で重複処理しない。ブロックツリーは文書順に1回走査し、各ブロックの担当処理を決定する。

### 5.3 共通データ

すべての見出しを次の形式へ変換する。

```ts
type OutlineNode = {
  id: string;
  blockClientId: string;
  blockName: string;
  level: 1 | 2 | 3 | 4 | 5 | 6;
  text: string;
  source: "core-heading" | "inner-block" | "adapter" | "html";
  navigable: boolean;
};
```

各項目の用途は次のとおりとする。

| 項目            | 用途                         |
| --------------- | ---------------------------- |
| `id`            | アウトライン項目の一意な識別 |
| `blockClientId` | 元ブロックの選択             |
| `blockName`     | アダプター判定と通知         |
| `level`         | 見出し階層の生成と診断       |
| `text`          | サイドバー表示               |
| `source`        | 取得元の識別とデバッグ       |
| `navigable`     | 対象ブロックへの移動可否     |

1つのブロックが複数の見出しを持つ場合は、見出しごとに一意な`id`を持つ複数の`OutlineNode`を生成する。

`id`は`<blockClientId>:<headingIndex>`で生成する。`headingIndex`は1ブロック内の見出し返却順を表すゼロ始まりの番号であり、標準Headingは常に`0`とする。無効なアダプター返却値が除外されても後続項目のIDが変わらないよう、アダプターでは除外前の返却位置を使用する。

このIDはエディターセッション内で、見出しテキストの編集やブロックの並べ替えに対して安定する。投稿データへ識別子を保存しないため、再読み込みをまたぐ永続IDは保証しない。

### 5.4 順序

見出しは、GutenbergのブロックツリーとinnerBlocksの順序に従って並べる。

アダプターが複数の見出しを返す場合は、その返却順を維持する。

### 5.5 HTML解析

`core/html`と`core/freeform`では、保存されている静的HTMLから`h1`から`h6`だけを抽出する。

次は実行しない。

- HTMLのブラウザー表示
- スクリプト
- ショートコード
- PHP
- 動的なレンダリング処理

解析に失敗した場合は、そのブロック由来の見出しを除外し、不完全なアウトラインとして通知する。

## 6. ブロックアダプター

### 6.1 目的

アダプターは、カスタムブロック固有の属性をYamabiko Outline共通の`OutlineNode`へ変換する。

### 6.2 JavaScript登録例

```ts
registerYamabikoOutlineAdapter({
  blockName: "example/faq",

  getOutlineNodes(block) {
    return [
      {
        level: block.attributes.headingLevel,
        text: block.attributes.title,
      },
    ];
  },
});
```

#### 6.2.1 Phase 1の内部契約

内部アダプターの最小インターフェースは次のとおりとする。アダプターは`OutlineNode`のID、ブロック情報、取得元を決めず、見出し固有の情報だけを返す。

```ts
type AdapterOutlineNode = {
  level: 1 | 2 | 3 | 4 | 5 | 6;
  text: string;
  navigable?: boolean;
};

type OutlineAdapter = {
  blockName: string;
  getOutlineNodes(block: Block): readonly AdapterOutlineNode[];
};
```

Registryへの接続時は、次を実行時にも検証する。

- `blockName`は登録済みブロック名と一致する空でない文字列である
- `getOutlineNodes`の返却値は配列である
- `level`は1から6の整数である
- `text`は文字列である。空文字列は診断対象として保持する
- `navigable`は省略可能な真偽値であり、省略時は`true`とする
- 不正な項目だけを除外し、アダプターの例外は対象ブロック内へ隔離する
- 同じ`blockName`の重複登録を拒否する

Phase 1では型と項目検証だけを製品コードへ含め、Registryとアダプター実行処理はPhase 2で実装する。

### 6.3 責務

アダプターは次だけを担当する。

- 対象ブロック名
- 見出しテキスト
- 見出しレベル
- 複数見出しの順序
- 必要に応じた移動可否

アダプターは次を行わない。

- ブロック内容の変更
- ブロックの移動
- 見出しレベルの自動修正
- HTMLやPHPの実行
- WordPress標準制約の変更

### 6.4 Registry

`Outline Adapter Registry`は、ブロック名をキーとしてアダプターを管理する。

Registryは次を保証する。

- 同じブロック名への重複登録を検出する
- アダプターの例外をほかのブロックから隔離する
- 不正な返却値を除外する
- 登録順に依存しない
- 未登録ブロックを安全に無視する

### 6.5 将来の公開API

MVPではアダプターを内部APIとして実装する。

公開APIの契約、バージョニング、開発者向け仕様は、内部APIを複数のブロックで検証した後に別途設計する。

### 6.6 PHP-onlyブロック

PHP-onlyブロック向けには、PHP側で見出しテキストと見出しレベルを持つ属性名を宣言し、その登録情報をエディターへ渡す方式を候補とする。

具体的な登録APIは製品化フェーズで定義する。

PHPの`render_callback`をアウトライン更新のたびに実行し、生成HTMLを解析する方式は採用しない。

## 7. 対応ブロックの処理方式

### 7.1 標準Resolver

次は`Standard Heading Resolver`で処理する。

- `core/heading`
- innerBlocks内の`core/heading`

### 7.2 組み込み処理

次は組み込みResolverまたはParserで処理する。

| ブロック                 | 処理                                 |
| ------------------------ | ------------------------------------ |
| `core/accordion-heading` | 属性から見出しレベルとテキストを取得 |
| `core/html`              | 静的HTMLからH1からH6を抽出           |
| `core/freeform`          | 静的HTMLからH1からH6を抽出           |
| テスト用カスタムブロック | 内部アダプターで取得                 |

`core/accordion-heading`の正式な見出しテキスト属性は`title`、保存される見出しレベル属性は`level`である。`level`は親`core/accordion`の`headingLevel`から子へ同期され、保存時に未設定の場合は`3`として扱われる。これはWordPress 7.0対応の[`accordion-heading/block.json`](https://github.com/WordPress/gutenberg/blob/wp/7.0/packages/block-library/src/accordion-heading/block.json)、[`accordion/edit.js`](https://github.com/WordPress/gutenberg/blob/wp/7.0/packages/block-library/src/accordion/edit.js)、[`accordion-heading/save.js`](https://github.com/WordPress/gutenberg/blob/wp/7.0/packages/block-library/src/accordion-heading/save.js)で確認した。Phase 1ではこの契約だけを記録し、アウトラインへの変換はPhase 2で実装する。

### 7.3 制限付き処理

同期パターンは、WordPress Data Storeから展開済みのブロックツリーを安全に取得できる場合だけ処理する。

動的ブロックとPHP-onlyブロックは、登録済みアダプターまたは宣言済み属性から見出し情報を取得できる場合だけ処理する。

確実に取得できない見出しは推測しない。

## 8. 対象ブロックへの移動

### 8.1 処理手順

アウトライン項目が選択された場合は、次の順で処理する。

1. `navigable`と`blockClientId`を確認する
2. 元ブロックが現在のブロックツリーに存在することを確認する
3. 必要に応じて折りたたまれた親を展開する
4. WordPress Data Storeを通して元ブロックを選択する
5. 標準編集キャンバス上の対象位置へスクロールする
6. 可能な場合だけ見出し編集部分へフォーカスする

### 8.2 カスタムブロック

カスタムブロック内部の個別見出しへ直接フォーカスできない場合は、元ブロックの選択とスクロールまでを正常動作とする。

1つのブロックに複数の見出しがあり、それぞれの編集位置を特定できない場合も同様とする。

### 8.3 移動不能

次の場合は移動を実行しない。

- `navigable`が`false`
- `blockClientId`が存在しない
- 対象ブロックが削除済み
- 現在のエディターで対象を選択できない

項目はアウトラインへ表示したままにし、移動できない理由を示す。

## 9. 構造診断

### 9.1 診断項目

次を診断する。

- H1が複数存在する
- 見出しレベルが飛んでいる
- 空の見出しがある
- ページ内に見出しがない
- 同一階層に同じ見出しが複数存在する

### 9.2 診断レベル

| 診断                 | レベル |
| -------------------- | ------ |
| H1の複数使用         | 警告   |
| 見出しレベルの飛び   | 警告   |
| 空見出し             | 警告   |
| 見出しなし           | 情報   |
| 同一階層の重複見出し | 提案   |

自動修正は行わない。

診断項目に対象ブロックが存在する場合は、選択によって対象ブロックへ移動できるようにする。

## 10. 不完全なアウトライン

### 10.1 通知条件

次の場合に、アウトラインが不完全な可能性を通知する。

- 製品内の明示的な見出し候補一覧にあるブロックに、対応するResolver、アダプター、またはParserがない
- PHP-onlyブロックから見出し情報を取得できない
- HTMLまたはClassicブロックの解析に失敗した
- 同期パターンを安全に展開できない
- アダプターが例外を発生させた
- アダプターが不正な見出し情報を返した

未対応ブロックの最小判定条件は「見出しを生成することを製品がブロック名単位で明示的に把握していること」とする。カスタム名前空間、動的ブロック、`render_callback`の有無だけでは見出し生成を判断できないため、それらだけを理由に通知しない。将来の明示的な宣言または登録がない未知のブロックは推測せず、誤検知を避ける。

### 10.2 表示

```text
この文書には、見出し情報を取得できないブロックが1件あります。
アウトラインが一部不完全な可能性があります。
```

可能であれば、対象ブロックの種類と件数を表示する。

見出しの存在、内容、レベルは推測しない。

未対応ブロックが存在しても、取得済みの見出しと診断結果は表示する。

## 11. システム構成

### 11.1 モジュール

- `Document Outline Sidebar`
- `Block Tree Selector`
- `Standard Heading Resolver`
- `Outline Adapter Registry`
- `HTML Heading Parser`
- `Outline Diagnostics`
- `Block Navigator`

### 11.2 責務

| モジュール                | 責務                               |
| ------------------------- | ---------------------------------- |
| Document Outline Sidebar  | アウトライン、診断、通知の表示     |
| Block Tree Selector       | Data Storeからのブロックツリー取得 |
| Standard Heading Resolver | 標準Headingの変換                  |
| Outline Adapter Registry  | ブロック別アダプターの管理         |
| HTML Heading Parser       | 静的HTMLからの見出し抽出           |
| Outline Diagnostics       | 見出し構造の診断                   |
| Block Navigator           | 選択、スクロール、フォーカス       |

## 12. 状態管理と更新

- ブロックツリーはWordPress Data Storeから取得する
- Yamabiko Outline独自のブロックツリーを保存しない
- ブロックの追加、変更、削除に応じてアウトラインを更新する
- 投稿本文へYamabiko Outline固有のデータを追加しない
- 一時的なUI状態だけをプラグイン内部で保持する
- 不要な全再計算を避け、変更の影響範囲に応じて再生成する

## 13. 非機能要件

### 13.1 パフォーマンス

- 100ブロック程度の投稿で快適に表示できること
- ブロック編集を妨げる明確な入力遅延を発生させないこと
- 最適化は実測結果に基づいて追加すること

### 13.2 アクセシビリティ

- キーボードでアウトライン項目を移動できること
- Enterキーで対象ブロックを選択できること
- 警告や移動不能状態を色だけで表現しないこと
- フォーカス移動の結果を適切に伝えること

### 13.3 セキュリティ

- HTML、スクリプト、ショートコード、PHPを実行しないこと
- 表示テキストを適切にエスケープすること
- アダプターから受け取る値を検証すること
- 将来サーバー処理を追加する場合は、権限とNonceを検証すること

### 13.4 保守性

- Gutenberg内部DOMへの依存を避けること
- Resolver、Parser、Registry、Diagnostics、Navigatorを分離すること
- 1つのアダプターの失敗で画面全体を停止しないこと
- 公開APIの互換性を管理できる構成にすること

## 14. エラー処理

- アダプター内の例外を捕捉し、ほかの処理を継続する
- 不正なアダプター返却値を除外する
- 見出しレベルが1から6の範囲外の場合は除外する
- 空の見出しテキストは診断対象として保持する
- HTML解析に失敗しても、ほかの見出しを表示する
- 移動対象が存在しない場合は通知して中止する
- ブロックが変更または削除された場合は最新状態へ同期する

## 15. テスト方針

### 15.1 単体テスト

- 標準HeadingとinnerBlocksからのアウトライン生成
- アダプターからのアウトライン生成
- 1ブロック内の複数見出し
- 一意なノードID
- HTMLからの見出し抽出
- 見出し診断
- 不正なアダプター返却値
- アダプター例外の隔離
- `navigable`による移動可否

### 15.2 結合・E2Eテスト

- サイドバーの起動
- ブロック変更時の更新
- 見出し選択による親展開、選択、スクロール
- Accordion、HTML、Classicの表示
- 未対応ブロックが存在しても停止しないこと
- 不完全なアウトライン通知
- キーボード操作
- プラグイン停止後に投稿内容へ影響しないこと

## 16. 技術的な未決事項
