## 2. 目的と責務

本書は、SortableJS版 Table Reorder のアクセシビリティ要件 `A11Y-FR-01` ～ `A11Y-FR-12` を、どのような利用者向けUI・操作・状態・情報提供で実現するかを定義する。

通常のPC・タッチ操作、結合セルを含む移動可否、データ保持、Undo、対象範囲などは `table-reorder-sortablejs-requirements.md` を正とする。本書ではそれらを再定義せず、キーボード操作およびドラッグを必要としない単一ポインター操作にも同じ制約を適用する方法を定める。

#199 は設計検討記録として参照するが、記載内容をそのまま確定仕様とはしない。特に、状態や専用UIを必要以上に増やさず、要件を満たすために必要な利用者向けの振る舞いだけを基本設計として確定する。

TypeScript / CSS、DOM取得、イベント登録、内部API、具体的なコンポーネント構成などの実装方法は本書の対象外とする。

## 3. 設計原則

1. ポインターDnD、キーボード操作、ドラッグを必要としない単一ポインター操作で、同じ移動可否と確定結果を共有する。
2. 有効な移動を確定した場合だけ行順を変更し、キャンセルまたは無効な操作ではデータを変更しない。
3. 一回の行移動は一回のUndoで戻せる単位とする。
4. 操作対象は「移動可能な本文行」とし、複数行にまたがる結合セルの範囲内の行は移動対象にしない。
5. 複数行にまたがる結合セルの途中を移動先にせず、結合範囲外の行は結合範囲全体を越えた有効な位置へ移動できる。
6. 行の並べ替えUIは、入力方式ごとに別機能として分断せず、同じ対象行と操作結果を利用者が追跡できるようにする。
7. Tableブロックをキーボードで選択しただけではTable Reorderのためにフォーカスを移動せず、Gutenberg本来の操作文脈を維持する。
8. PCのキーボード操作では、ブロックツールバーの「行を並べ替え」操作を行の並べ替えUIへの明示的な入口とし、PC用の並べ替えモードは新設しない。
9. PC・タッチとも、行を動かすポインター操作は共通の行ハンドルを入口とする。ハンドルをドラッグした場合はDnD、ドラッグせず実行した場合は単一ポインター移動先選択として扱う。
10. 待機中のフォーカス移動は、可能な限りブラウザーおよびGutenbergの通常のフォーカス順を利用する。
11. 操作案内は外部マニュアルを前提とせず確認できるようにするが、常時大きな説明を表示しない。
12. 支援技術への通知は状態変化と操作結果に限定し、同じ内容を不要に繰り返さない。
13. iframe・non-iframeで利用者向けの操作、フォーカス、案内、通知の意味を変えない。

## 4. 利用者向けUI

### 4.1 行の並べ替えUI

移動可能な各行に、その行を並べ替えるための操作UIを対応付ける。

このUIは、少なくとも次を満たす。

- キーボードだけで到達できる。
- 対象行を識別できるアクセシブルな名前を持つ。
- 操作可能なUIとして役割を支援技術から判別できる。
- 並べ替え操作中かどうかなど、利用者が判断する必要がある状態を支援技術から確認できる。
- キーボードフォーカスを視覚的に確認できる。
- hoverだけを表示・到達の唯一の条件にしない。

PCの通常のポインターDnDでは、基本要件どおり移動可能な行へのhoverでその行の左端にハンドルを表示する。行全体はハンドルの表示検知領域に限り、表示されたハンドルを直接ドラッグしてDnDを開始する既存操作は変更しない。ポインターDnDの開始時にTable Reorderのための初期フォーカス移動は行わない。

PCでは同じハンドルを単一ポインター操作の入口としても使用する。ハンドルをドラッグした場合は既存のポインターDnDとして扱い、ドラッグせずクリックした場合は4.2の単一ポインター操作を開始する。

タッチ端末の「行を並び替え」モードでは、移動可能な各行に同じ行ハンドルを常時表示する。セルの通常タップは編集、行ハンドルのタップはドラッグを必要としない単一ポインター移動先選択、行ハンドルのドラッグはDnDとして扱う。行そのものの長押しはDnDの開始操作にしない。

キーボードで行の並べ替えUIへフォーカスした場合は、hoverしていなくても操作対象を視認できる状態にする。

複数行にまたがる結合セルの範囲内の行は移動対象ではないため、移動可能な行と同じ並べ替え操作UIを提供しない。利用者が移動不能理由を知る必要がある場面では、操作案内または支援技術への通知によって理由を確認できるようにする。

### 4.2 ドラッグを必要としない単一ポインター操作UI

PC・タッチともに、ドラッグせず単一ポインター操作だけで一行の移動を完了できるようにする。

#### PC

PCでは、既存のhoverによるハンドル表示をそのまま利用し、次の流れとする。

1. 移動したい行へhoverし、その行の左端にハンドルを表示する。hoverしただけではフォーカスを変更しない。
2. 表示されたハンドルをドラッグせずクリックする。クリックした行の並べ替えUIをフォーカス対象とし、その行を移動対象として選択する。
3. 選択後、その行を挿入できる有効な移動先を操作UIとして表示する。移動先UIを表示しただけでは、最初の移動先へフォーカスを自動移動せず、対象行の並べ替えUIにフォーカスを維持する。
4. 利用者が任意の移動先UIをクリックする。クリック時は、その移動先UIがフォーカス対象となる。
5. 有効な移動を確定した後は、移動後の同じ行に対応する行の並べ替えUIへフォーカスを移し、利用者が移動した行を見失わないようにする。
6. 確定せず操作を終了できるキャンセル手段を提供する。キャンセル後は、操作開始時の対象行の並べ替えUIへフォーカスを戻す。

PCでは単一ポインター操作専用の開始ボタンや並べ替えモードを追加しない。同じハンドルに対して、ドラッグは既存のポインターDnD、クリックは単一ポインター操作として扱う。ドラッグとして開始・完了した操作を、続けてクリック操作として処理しない。

セルそのもののクリックは従来どおりセル編集に使用し、単一ポインター操作の開始には使用しない。ハンドルおよびその操作領域は、先頭セルの内容、選択、編集に必要なポインター操作を妨げないようにする。

#### タッチ

タッチ端末では、基本要件の「行を並び替え」モードの中で次の流れとする。

1. 移動可能な行に対応する行ハンドルをタップして、その行を移動対象として選択する。
2. 選択後、その行を挿入できる有効な移動先を操作UIとして表示する。
3. 移動先をタップすると、その位置への移動を確定する。
4. 案内に併設する「キャンセル」操作をタップすると、行順を変更せず移動先選択だけを終了し、「行を並び替え」モードへ戻る。

セルをタップした場合は、基本要件 `TOUCH-03` に従って通常のセル編集として扱い、単一ポインター操作やDnDを開始しない。行ハンドルをドラッグした場合は基本要件 `TOUCH-02` に従って SortableJS DnD を開始する。行ハンドルのタップはドラッグを必要としない移動先選択の入口とし、同じハンドル上のドラッグとは別の結果として扱う。行そのものの長押しではDnDを開始しない。

モード開始時に特定の行へ自動的にフォーカスを移したり移動対象を決めたりせず、その後に利用者が行ハンドルを操作した行を移動対象とする。

単一ポインター移動先選択中は、移動先を探すために縦スクロールしても案内と「キャンセル」操作を画面内で確認・操作できる状態を保つ。移動先UI上からスワイプを開始した場合も、スクロールジェスチャーだけでは移動を確定せず、移動先へのタップと区別する。「行を並び替え」モードをOFFにした場合は、進行中の移動先選択を行順を変更せず終了する。案内を画面内に保つための `sticky` / `fixed` 等の具体的な方法は実装時に決定する。

PC・タッチともに、移動先UIは「行そのもの」ではなく、どこへ挿入されるかを利用者が判断できる行間の位置として表現する。複数行にまたがる結合セルの範囲の途中は移動先として表示しない。

### 4.3 ポインター操作UIのターゲットサイズ

行の並べ替えUIと、単一ポインター操作で表示する移動先UIは、PC・タッチの双方で WCAG 2.2 2.5.8 Target Size (Minimum) を満たす操作領域を確保する。

- 視覚上のアイコンや線が小さい場合でも、操作可能領域は必要な大きさを確保する。
- 隣接する操作対象を誤って選びやすい密集配置を避ける。
- 具体的なpx値、余白、CSSによる確保方法は実装時に決定する。

## 5. キーボード操作

### 5.1 キーボード操作への入口

Tableブロックをキーボードで選択しただけでは、Table Reorderは行の並べ替えUIへフォーカスを移さない。Tableの選択・編集はGutenberg本来のフォーカス状態を維持する。

PCのブロックツールバーに「行を並べ替え」操作を提供し、キーボード利用者がこの操作を実行したときに行の並べ替えUIへフォーカスを移す。これはPC用の並べ替えモードを開始する操作ではなく、行の並べ替えUIへ移動するための入口とする。この時点ではまだ行の並べ替えは開始しない。

フォーカス先は次の優先順で決定する。

1. 現在操作中または編集中の本文行を特定でき、その行が移動可能な場合は、その行の並べ替えUIへフォーカスする。
2. 現在の本文行を特定できない場合は、先頭の移動可能な行の並べ替えUIへフォーカスする。
3. 現在の本文行を特定できるが、その行が複数行にまたがる結合セルの範囲内などの理由で移動不能な場合は、別の行へ自動的にフォーカスを移さない。「行を並べ替え」操作にフォーカスを維持し、移動できない理由を伝える。
4. 移動可能な本文行が存在しない場合も、「行を並べ替え」操作にフォーカスを維持し、並べ替え可能な行がないことを伝える。

この入口を実行しただけでは状態を「キーボード並べ替え中」へ変更しない。行の並べ替えUIへフォーカスした後、利用者が `Enter` または `Space` を押した時点で並べ替えを開始する。

タッチ端末の「行を並び替え」モードは基本要件どおりのタッチ操作として扱い、本項のPCキーボード用入口とは役割を分ける。タッチ操作ではモード開始時の初期フォーカスを定義せず、セルの通常タップは編集、行ハンドルのドラッグはDnD、行ハンドルのタップは単一ポインター操作の入口として扱う。

### 5.2 待機中のアクセス

行の並べ替えUIへフォーカスした後は、通常の `Tab` / `Shift + Tab` によるフォーカス移動で、移動可能な行の並べ替えUIへ表内の論理的な順序でアクセスできるようにする。

Table Reorder独自のTab循環は設けない。先頭または末尾の行の並べ替えUIを越えた場合は、Gutenbergの通常のフォーカス順に従ってTable Reorder外へ移動できる。

### 5.3 並べ替え開始

フォーカス中の行の並べ替えUIで、次のキーを使用する。

- `Enter` または `Space`: 並べ替え開始

開始時は、その行の並べ替えUIからフォーカスを移動しない。対象行を「キーボード並べ替え中」の状態として明確にし、対象行と現在位置を支援技術へ伝える。

### 5.4 移動先の変更

キーボード並べ替え中は、次のキーで移動先候補を変更する。

- `ArrowUp`: 現在位置より前にある次の有効な移動先へ進む
- `ArrowDown`: 現在位置より後にある次の有効な移動先へ進む

「次の有効な移動先」は、基本要件の移動可否を満たす位置を指す。複数行にまたがる結合セルがある場合は、その途中を候補にせず、結合範囲全体を越えた次の有効な位置へ進む。

先頭・末尾など、それ以上移動できる位置がない場合は候補を変更せず、移動できないことを利用者へ伝える。

### 5.5 確定とキャンセル

キーボード並べ替え中は、次のキーを使用する。

- `Enter` または `Space`: 現在の移動先で確定
- `Escape`: キャンセル

確定では、有効な移動先が元の位置と異なる場合だけ行順を更新する。同じ位置の確定は行順を変更せず、不要なUndo履歴を増やさない。

キャンセルでは行順を変更しない。

### 5.6 並べ替え中のフォーカス

キーボード並べ替え中は、確定またはキャンセルするまで操作対象の行の並べ替えUIにフォーカスを維持する。`Tab` / `Shift + Tab` で別の操作へ移動させず、現在の並べ替え操作を完了またはキャンセルしてから通常のフォーカス移動へ戻る。

確定後は、移動後の同じ行に対応する並べ替えUIへフォーカスを維持する。キャンセル後は、操作開始時と同じ行の並べ替えUIへフォーカスを戻す。

これにより、行の位置が変わっても利用者が操作対象を見失わず、そのまま次の操作を継続できるようにする。

## 6. 状態遷移

利用者から見える主要状態は、必要最小限の次の3状態とする。

| 状態 | 利用者から見える意味 |
|---|---|
| 待機 | 行の並べ替え操作を開始できる通常状態 |
| キーボード並べ替え中 | 一つの行をキーボードで移動している状態 |
| 単一ポインター移動先選択中 | 一つの行を選択し、クリックまたはタップする移動先を選んでいる状態 |

「行を並べ替え」操作から行の並べ替えUIへフォーカスを移しただけでは待機のままとし、独立したモードや状態を追加しない。

確定とキャンセルは独立した状態として保持せず、各操作状態から待機へ戻る遷移として扱う。

- 待機 → キーボード並べ替え中: 行の並べ替えUIで `Enter` / `Space` を押して開始
- キーボード並べ替え中 → 待機: 確定またはキャンセル
- 待機 → 単一ポインター移動先選択中: PCでは表示されたハンドルをクリック、タッチでは移動可能な行のハンドルをタップして開始
- 単一ポインター移動先選択中 → 待機: 移動先を選択して確定、またはキャンセル

ポインターDnDは基本要件で定義済みの既存操作として扱い、本書の追加状態を不必要に共有しない。ただし、同時に複数の並べ替え操作が進行しないようにする。

## 7. フォーカス管理と可視性

### 7.1 フォーカス可視性

キーボードフォーカスを受けた行の並べ替えUIは、hover状態や選択状態だけに依存せず視覚的に識別できるようにする。

キーボード並べ替え中は、「フォーカスされていること」と「並べ替え中であること」を区別して理解できる表示とする。別の行が同時にフォーカスされているように見える表現は避ける。

PCの単一ポインター操作では、ハンドルをクリックして移動対象を選択した後も、その対象行の並べ替えUIにフォーカスがあることを視覚的に確認できるようにする。

### 7.2 Focus Not Obscured

キーボードフォーカスを受けた行の並べ替えUIを、Table Reorder自身が表示する案内、移動先UI、状態表示などによって完全に隠さない。

フォーカスが別の行へ復元・維持された場合も、その操作対象を利用者が視認できる状態を保つ。必要なスクロールやUI配置調整の具体的な方法は実装時に決定する。

### 7.3 Table選択時とタッチ操作のフォーカス

Tableブロックをキーボードで選択しただけでは、Table Reorderのための初期フォーカスを設定しない。Gutenberg本来のフォーカス状態を維持し、利用者が「行を並べ替え」操作を実行した時点で初めて5.1の規則に従って行の並べ替えUIへフォーカスを移す。

タッチ端末では、「行を並び替え」モードを開始しただけでは特定の行へフォーカスを移さず、移動対象も決定しない。行ハンドルのドラッグでは利用者がドラッグした行を、ドラッグを必要としない単一ポインター操作では利用者が行ハンドルをタップした行を、それぞれ操作対象とするため、タッチ操作固有の初期フォーカスは定義しない。セルの通常タップは通常のセル編集として扱う。

外付けキーボード等でキーボード操作を行う場合は、タッチ操作のフォーカス規則ではなく5章のキーボード操作を適用する。

### 7.4 スクロール追従と操作文脈の維持

行の並べ替えによって現在の操作対象または移動先候補が表示領域の外へ進む場合は、操作に合わせて縦方向の表示を追従させる。

この方針は、ポインターDnD、キーボード操作、ドラッグを必要としない単一ポインター操作に共通して適用する。

キーボード操作の表示追従は、`ArrowUp` / `ArrowDown` によって移動先候補が実際に変更された場合にだけ行う。先頭・末尾など、それ以上進めず候補が変更されない操作では、境界到達を支援技術へ伝えても不要な縦スクロールは行わない。

キーボード並べ替え中は、`Enter` / `Space` で確定した場合の挿入位置を常に判断できるよう、現在の挿入位置を示す挿入線と、その直前・直後に存在する行をTable Reorder自身の操作ガイド等で隠さない。先頭・末尾の候補でも同じ条件を満たす。必要に応じて縦スクロールで追従し、単に対象行がviewport内にあるかではなく、操作ガイド等が占有する領域を除いた実質的な可視領域を基準に判定する。

- 下方向へ移動している場合は、現在の操作対象または移動先候補に加えて、原則としてその下の次の行または次の有効な移動先を視認できる状態を保つ。
- 上方向へ移動している場合は、現在の操作対象または移動先候補に加えて、原則としてその上の次の行または次の有効な移動先を視認できる状態を保つ。
- 複数行にまたがる結合セルがある場合は、結合範囲の途中ではなく、移動方向側の次の有効な移動先を確認できることを優先する。
- 行の高さが表示領域を超えるなど、隣接する一行を同時に表示できない場合は、現在の操作対象・移動先候補と移動方向を見失わない範囲で可能な表示を確保する。
- 表示追従は、現在候補と移動方向を確認するために必要な範囲に留め、操作文脈を見失うほどの過剰な画面移動を避ける。

ポインターDnDでは、表示領域の上端または下端へ操作が進んだときに、ドラッグ操作を継続したまま縦スクロールで追従できるようにする。キーボード操作では、移動先候補が実際に変更された場合だけ、その候補を視認できる位置へ必要最小限の表示を追従させる。単一ポインター操作では、選択可能な移動先を確認しながら必要な位置まで縦スクロールできる状態を保つ。

スクロール開始位置、速度、余白量、具体的なスクロールAPIなどの実装詳細は実装時に決定する。

## 8. 利用者向けメッセージ仕様

1. 画面表示メッセージ
2. 支援技術向け動的通知
3. 操作UIのアクセシブルな名前・説明

3系統とも英語を翻訳元とし、日本語を翻訳として提供する。文言、表示・通知契機、消える契機、重複抑制を本章で確定し、実装計画や各controllerで新しい文言仕様を決めない。

### 8.5 メッセージ競合時の優先関係

同じTable内では、画面表示メッセージを次の優先順で扱い、同じ操作文脈の案内を重ねて表示しない。

1. `VIS-ROWSPAN-ERROR` または `VIS-NO-MOVABLE-ROWS`
2. `VIS-KEYBOARD-ACTIVE` または入力方式に応じた `VIS-PC-POINTER-ACTIVE` / `VIS-TOUCH-POINTER-ACTIVE`
3. `VIS-TOUCH-MODE`
4. `VIS-PC-HANDLE-HOVER` または `VIS-ROW-HANDLE-FOCUS`

操作状態が変わった場合は、直前の案内を残したまま追加せず、新しい状態の案内へ置き換える。一時的なエラー表示が終了した後も操作状態が継続している場合は、その状態に対応する通常案内を再表示する。hoverとキーボードフォーカスが同時に成立する場合は、実際の入力方式に対応する案内を一つだけ表示する。

`VIS-TOUCH-COACHMARK` は、通常案内またはエラーの表示中には表示しない。コーチマーク表示中にモード開始、移動対象選択、エラー等が発生した場合はコーチマークを閉じ、現在の状態に必要な案内へ置き換える。

### 8.6 タッチ端末の初回コーチマーク

初回コーチマークの役割は、「表の行を並べ替えられること」と「ツールバーの『行を並べ替え』から開始できること」を知らせる機能発見の補助に限定する。

- タッチ端末でTable Reorderを初めて利用する利用者にだけ自動表示する。
- 利用者が閉じた後は、ページ再読み込みや投稿を開き直した場合も自動再表示しない。
- Tableを選択するたびに表示する常時案内にはしない。
- 大きなモーダルや複数ページのチュートリアルにはしない。
- モード開始後の操作方法は `VIS-TOUCH-MODE` と `VIS-TOUCH-POINTER-ACTIVE` で案内する。

PCは行へのhoverでハンドルを発見でき、ハンドルのツールチップで操作方法を再確認できるため、初回コーチマークを設けない。

### 8.7 多言語化と一元管理

- 英語をWordPress i18nの翻訳元とし、日本語はWordPressの翻訳データとして提供する。
- JavaScriptでは `@wordpress/i18n` の翻訳関数と `sprintf()` を使用し、`yamabiko-editor-tools` テキストドメインを使用する。
- 可変値を含む文言は番号付きの `%1$s` / `%2$d` 等を翻訳元へ含め、独自の名前付きトークン置換を実装しない。
- 必要なスクリプト翻訳はWordPress標準の仕組みで読み込む。
- `en` / `ja` の独自言語オブジェクトをTypeScript内に持たない。
- 本章のメッセージIDと実装上の定義を対応付け、Table Reorderの利用者向け文言を一つのメッセージモジュールへ集約する。
- controller、UI処理、通知処理へ利用者向け文字列を直接記述しない。
- 固定文言だけでなく、行位置、移動先、行の代表情報等を含む文もメッセージモジュールから提供する。
- 将来の言語追加では操作ロジックを変更せず、翻訳データの追加で対応できる構造とする。

メッセージモジュールは、本章で確定した文言を提供する責務に限定する。表示優先度の管理、WordPress UIの選定、ARIA・DOM構造などの具体的な実装は、本章の利用者向け意味を変えない範囲で実装時に決定する。

## 9. 結合セルと基本要件の適用

キーボード操作と単一ポインター操作にも、SortableJS版基本要件の移動制約をそのまま適用する。

### 複数行にまたがる結合セル

- 結合範囲内の行そのものは移動対象にしない。
- 結合範囲の途中を移動先にしない。
- 結合範囲外の行は、結合範囲全体を越えた前後の有効な位置へ移動できる。
- 無効な操作では行順を変更しない。
- 移動できない理由を利用者および必要に応じて支援技術から確認できるようにする。

### 複数列にまたがる結合セル

複数列にまたがる結合セルだけを含む行は、基本要件上安全に移動できる場合はキーボード操作・単一ポインター操作でも禁止しない。

### データ保持・Undo・対象範囲

- 移動後もセル内容、セル属性、装飾を保持する。
- 一回の有効な移動を一回のUndoで元に戻せる。
- `tbody`内の本文行だけを対象とし、`thead`、`tbody`、`tfoot`をまたぐ移動を行わない。
- Table以外のブロックや対象外のTableへ影響を与えない。

## 10. iframe・non-iframe対応

iframe・non-iframeの両方で、次の利用者向け動作を同じ意味で成立させる。

- Table選択時にはTable Reorderのために自動でフォーカスを移さない。
- 「行を並べ替え」操作から、現在行または先頭の移動可能な行の並べ替えUIへキーボードで移動できる。
- PCでは移動可能な行へのhoverで左端にハンドルを表示し、同じハンドルをドラッグとクリックの両方の入口として利用できる。行全体はドラッグ開始領域にしない。
- タッチでは並べ替えモード中に行ハンドルを表示し、セルの通常タップによる編集、行ハンドルのドラッグによるDnD、行ハンドルのタップによる単一ポインター操作を区別できる。行そのものの長押しではDnDを開始しない。
- キーボード操作のキー割り当てと結果が同じである。
- 単一ポインター操作の操作フローと結果が同じである。
- フォーカス維持・復元の考え方が同じである。
- 操作に応じた縦スクロール追従と、移動方向側の次の操作先を確認できる表示方針が同じである。
- 操作案内の内容と確認手段が同じである。
- 支援技術へ提供する対象・状態・結果・移動不能理由の意味が同じである。

DOM取得、イベント登録、フォーカス対象の探索方法、クリックとドラッグの内部判定方法など、編集環境ごとの具体的な実装差は実装側で吸収する。

## 11. 要件との対応

| 要件 | 基本設計上の対応 |
|---|---|
| A11Y-FR-01 キーボード完結 | ブロックツールバーの「行を並べ替え」操作から行の並べ替えUIへ移動し、`Enter` / `Space`で開始・確定、`ArrowUp` / `ArrowDown`で次の有効な移動先へ進み、`Escape`でキャンセルする。 |
| A11Y-FR-02 単一ポインター操作 | PCでは既存ハンドルをクリックして対象行を選択し、有効な行間の移動先をクリックして確定する。タッチでは並べ替えモード中の行ハンドルをタップして対象行を選択し、移動先をタップして確定する。セルの通常タップは編集、同じ行ハンドルのドラッグはDnDとして維持する。 |
| A11Y-FR-03 ターゲットサイズ | 行の並べ替えUIと移動先UIで、PC・タッチ双方の WCAG 2.2 2.5.8 を満たす操作領域を確保する。 |
| A11Y-FR-04 論理的なアクセス順 | 「行を並べ替え」操作から現在行または先頭の移動可能な行へ入り、その後は通常のTab順で移動可能な行の並べ替えUIへ表内の論理順にアクセスする。 |
| A11Y-FR-05 操作文脈 | Table選択だけではフォーカスを変えず、キーボード入口では現在行を優先して対象行へ移る。PC単一ポインター操作ではハンドルクリック後も対象行にフォーカスを維持し、確定後は移動後の同じ行へ戻す。キーボード並べ替え中は挿入線とその直前・直後に存在する行を案内で隠さず、実質的な可視領域を基準に必要な縦スクロールを追従させる。 |
| A11Y-FR-06 フォーカス可視性 | フォーカス中の並べ替えUIをhoverに依存せず視覚的に識別できるようにする。 |
| A11Y-FR-07 フォーカス遮蔽 | Table Reorder自身のUIでフォーカス対象を完全に隠さず、必要な縦スクロールを含めて遷移後も視認できる状態を維持する。 |
| A11Y-FR-08 操作案内 | 8.2の画面表示メッセージ表を正本とし、PCのツールチップ、操作中のインライン案内、タッチの初回コーチマーク、rowspanエラー、移動可能行がない場合の警告について、表示形式・位置・文言・表示契機・消える契機を定義する。 |
| A11Y-FR-09 支援技術への情報提供 | 8.3の動的通知表を正本とし、開始、移動先選択待ち、移動先変更、確定、キャンセル、境界、結合セル制約、移動可能行なしの通知文言・可変情報・重複抑制を定義する。 |
| A11Y-FR-10 名前・役割・状態 | 8.4の名前・説明表を正本とし、行の並べ替えUI、移動先UI、キャンセル操作、Toolbar入口を識別する英語原文・日本語・可変情報を定義する。対象行は現在位置と行内容の代表情報で区別する。 |
| A11Y-FR-11 基本要件の共有 | 結合セル、データ保持、Undo、対象範囲、無効操作の基本要件をすべてのアクセシビリティ操作に共通適用する。 |
| A11Y-FR-12 編集環境 | iframe・non-iframeで同じ利用者向け操作、フォーカス、スクロール追従、案内、通知の意味を成立させる。 |

## 13. 完了確認

- `table-reorder-sortablejs-requirements.md` を基礎文書として参照している。
- `table-reorder-sortablejs-accessibility-requirements.md` をアクセシビリティ要件の正本として参照している。
- `A11Y-FR-01` ～ `A11Y-FR-12` のすべてについて基本設計上の対応を確認できる。
- Tableブロックをキーボードで選択しただけではTable Reorderのためにフォーカスを変更しない設計になっている。
- PCでは「行を並べ替え」操作をキーボード操作の入口とし、現在行を特定できる場合はその行、特定できない場合は先頭の移動可能な行の並べ替えUIへフォーカスする設計になっている。
- 「行を並べ替え」操作から行の並べ替えUIへ移動しただけでは並べ替えモードやキーボード並べ替えを開始しない設計になっている。
- PCの既存hoverによるハンドル表示とポインターDnDを変更せず、ポインターDnD開始時にはTable Reorderのための初期フォーカス移動を行わない設計になっている。
- PCでは同じハンドルをクリックすることで単一ポインター操作を開始し、ドラッグ操作とクリック操作を専用UIの追加なしに共存させる設計になっている。
- タッチでは並べ替えモード中の同じ行ハンドルを、タップによる単一ポインター移動先選択とドラッグによるDnDの入口として共用する設計になっている。
- タッチでは行そのものの長押しでDnDを開始せず、セルの通常タップによる編集と行ハンドル外からの通常スクロールを妨げない設計になっている。
- PC単一ポインター操作では、ハンドルクリック後は対象行の並べ替えUIにフォーカスを維持し、移動先クリック後の確定時には移動後の同じ行の並べ替えUIへフォーカスする設計になっている。
- 画面表示メッセージ、支援技術向け動的通知、操作UIのアクセシブルな名前・説明を8章の別表に整理し、各メッセージIDに英語原文と日本語を定義している。
- 画面表示メッセージごとに、状態、表示対象、表示形式、表示位置・関連付け、表示契機、消える契機を定義している。
- Toolbar入口で現在行がrowspan制約により移動不能な場合と、移動可能な本文行がない場合は、フォーカスをToolbarに維持しながら画面表示と支援技術向け通知の両方で理由を伝える設計になっている。
- PCでは行へのhoverで表示されたハンドルのツールチップから、ドラッグとクリックの両操作を再確認できる設計になっている。
- キーボード並べ替え中と単一ポインター移動先選択中は、Table上部のインライン案内から次の操作と確定・キャンセル方法を継続して確認できる設計になっている。
- タッチの単一ポインター移動先選択中は、縦スクロールしても案内と明示的な「キャンセル」操作を確認・操作でき、スワイプだけでは移動を確定しない設計になっている。
- タッチ端末では初回コーチマークで機能とToolbar入口を案内し、閉じた後は自動再表示しない。PCには初回コーチマークを設けない設計になっている。
- 画面表示メッセージの競合時の優先関係と置き換え条件を定義し、確定・キャンセル・単純な移動境界では不要な画面表示を追加しない設計になっている。
- 支援技術向け動的通知ごとに通知契機、含める情報、重複抑制を定義し、具体的なARIA・DOM実装とは分離している。
- 利用者向け文言はWordPress標準i18nを使う一つのメッセージモジュールへ集約し、controller等へ直書きしない設計になっている。
- 可変値を含む文言はWordPress標準の `sprintf()` と番号付きプレースホルダーを使用し、対象行の代表情報と行位置を重複させない設計になっている。
- タッチ操作ではモード開始時の初期フォーカスを定義せず、セルの通常タップは編集、行ハンドルのドラッグは SortableJS DnD、行ハンドルのタップはドラッグを必要としない移動先選択として、それぞれ別の結果にしている。
- キーボード操作、単一ポインター操作、フォーカス管理、操作案内、支援技術への情報提供を整理している。
- Target Size と Focus Not Obscured への対応を整理している。
- 行の並べ替え中に必要な縦スクロールを追従させ、キーボード並べ替えでは挿入線とその直前・直後に存在する行をTable Reorderの案内で隠さず、移動方向側の次の行または次の有効な移動先を可能な範囲で確認できる設計になっている。
- 行の並べ替えUIのアクセシブルな名前・役割・状態・対象行の識別方法を整理している。
- 結合セル制約、データ保持、Undo、対象範囲をアクセシビリティ操作にも適用している。
- iframe・non-iframeの両方で同じ利用者向け動作を成立させる方針を整理している。
- #199 の検討を参考にしつつ、不要な状態や実装詳細をそのまま転記していない。
- 実装方法へ踏み込みすぎず、基本設計として必要十分な範囲に留めている。
