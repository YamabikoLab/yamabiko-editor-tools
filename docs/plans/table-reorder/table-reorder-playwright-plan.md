# Table Reorder Playwright テスト実装プラン

## 1. 文書情報

| 項目 | 内容 |
|---|---|
| 対象Issue | #118 |
| 親Issue | #116 |
| 後続Issue | #119 |
| 対象 | `table-reorder-controller.tsx` リファクタリング前の Playwright E2E テスト整備 |
| 目的 | リファクタリング前の主要なユーザー操作を、必要最小限の実ブラウザテストで固定する |

## 2. 目的

`src/editor-extensions/table-reorder/table-reorder-controller.tsx` の責務分割に入る前に、Jestでは保証しにくい実ブラウザ上の振る舞いを Playwright で固定する。

本プランでは E2E を網羅テストにせず、#119 のリファクタリングで壊れやすい次の境界だけを防護柵として確認する。

- 並べ替えモード開始時のフォーカス
- Tab / Shift+Tab による行ハンドル間のフォーカス移動
- キーボードによる開始、移動、確定、キャンセル
- DOM更新後の行順とフォーカス維持
- ポインターDnDによる基本的な行移動
- 行移動後の Undo / Redo と履歴単位
- hover可能な端末でのハンドル表示・非表示とセル編集への切り替え
- 通常幅 / 全幅テーブルでのhover挙動
- `colspan` / `rowspan` を含む代表的な結合セル制約
- 長距離キーボード移動時の必要最小限のスクロール追従
- iframe / non-iframe の編集環境差

純粋ロジックや細かな境界条件は #117 の Jest テストを正とし、Playwright で重複して検証しない。

## 3. 基本方針

- ユーザーから見える振る舞いを検証する。
- テスト本数を増やしすぎず、関連する主要フローは一つのシナリオへまとめる。
- 用途別のテストデータセットを用意し、異なる目的のテストへ不要な条件を混ぜない。
- テストデータのマークアップを各テストへ重複してベタ書きせず、必要最小限の fixture / builder として再利用する。
- `@wordpress/e2e-test-utils-playwright` が提供する fixture / helper を優先する。
- iframe / non-iframe の切り替えや canvas 取得を各テストへ散らさない。
- Gutenberg内部DOM、一時class、React state、dnd-kit内部状態へ過度に依存しない。
- 固定時間の `waitForTimeout()` でタイミング問題を隠さない。
- CSSアニメーションや座標の厳密値を完了条件にしない。
- テストのために本体仕様を変更しない。

## 4. 実装対象

### 4.1 Table Reorder E2E の共通準備

`tests/e2e/table-reorder.spec.ts` を基本とする。

必要な場合だけ、小さなテストヘルパーを `tests/e2e/` 配下へ切り出す。

共通化する候補は次のとおり。

1. 新規投稿を開く。
2. iframe / non-iframe を切り替える。
3. テスト用の Core Table ブロックを設定する。
4. 対象 editor canvas を取得する。
5. Table ブロックを選択する。
6. ブロックツールバーを表示する。
7. 「行を並べ替え」を有効にする。
8. 通常幅 / 全幅のTableを必要に応じて切り替える。

共通化は重複を減らす範囲に留め、E2E専用の大きな抽象化層は作らない。

### 4.2 用途別テストデータ

E2Eの目的ごとに、次の3種類のデータセットを用意する。

| データセット | 用途 | 内容 |
|---|---|---|
| `basicTable` | キーボード主要フロー、Tab移動、ポインターDnD、Undo / Redo、hover | 通常行4行程度。各行を画面上の内容から識別できる単純なTable。hover確認では同じデータを通常幅 / 全幅の2形態で使用する |
| `mergedCellsTable` | 結合セル制約の代表確認 | 8行程度。通常行、`colspan` のみを含む横結合行、`rowspan` を含む縦結合範囲を一つのTableに含める |
| `longTable` | 長距離スクロール追従 | 30行程度。結合セルなどの追加条件を含まない単純なTable |

#### `basicTable`

- 4行程度の単純な `tbody` とする。
- `Row 1`、`Row 2` のように、並び順を画面上の内容から判定できるデータにする。
- キーボード操作、Tab移動、ポインターDnD、Undo / Redo、hoverの基本フローではこのデータだけを使い、結合セルなど別の要因を持ち込まない。
- hoverの検証では同じ内容のTableを通常幅と全幅の2形態で使用し、データ内容の違いをテスト要因にしない。

#### `mergedCellsTable`

8行程度を目安として、少なくとも次の意味を持つ行を含める。

1. 通常行 A
2. 通常行 B
3. `colspan` のみを含む横結合行
4. 通常行 C
5. `rowspan` の開始行
6. `rowspan` の結合範囲に含まれる行
7. 通常行 D
8. 通常行 E

このデータセットは、結合セル制約の全組み合わせを網羅するためではなく、実ブラウザ上で次の対になる代表挙動が成立することを確認するために使用する。

- `colspan` だけの横結合行が存在しても、安全な行移動は許可される。
- `rowspan` の結合範囲を分断する行移動は拒否され、Table の行データは変更されない。

`rowspan` 範囲の細かな境界、non-movable row の算出、挿入位置ごとの可否などは #117 の Jest テストへ任せ、Playwright では網羅しない。

#### `longTable`

- `Row 01` から `Row 30` のように識別可能な30行程度の単純なTableとする。
- スクロール追従だけを検証できるよう、`rowspan`、`colspan`、複雑な装飾などは混ぜない。

#### 実装方法

具体的な Gutenberg のブロックマークアップ、および fixture / builder のファイル構成は、実装時に現在の Core Table ブロックの保存形式と既存E2E構成を確認して決定する。

次を守る。

- WordPress が正しく解釈できる現在の Core Table ブロック形式を使用する。
- 同じTableマークアップを複数テストへコピーしない。
- 通常幅 / 全幅は、可能な限り同じ `basicTable` の生成処理へ属性差だけを与えて表現する。
- データセット名や小さな生成関数で意図が分かる程度に留める。
- 汎用的なテストデータフレームワークは新設しない。
- データセットを作るために本体コードへテスト専用処理を追加しない。

### 4.3 キーボード主要フロー

#### 対象環境

- iframe
- non-iframe

#### テストデータ

`basicTable` を使用する。

#### 操作

1. 中間行のセルへフォーカスする。
2. 並べ替えモードをONにする。
3. 対応する本文行のハンドルへ初期フォーカスが移ることを確認する。
4. `Enter` でキーボード並べ替えを開始する。
5. `ArrowDown` または `ArrowUp` で一行移動する。
6. `Escape` でキャンセルする。
7. 行順が変更されていないことを確認する。
8. 対象行のハンドルへフォーカスが維持されていることを確認する。
9. 同じ行で再度キーボード並べ替えを開始する。
10. 一行移動する。
11. `Enter` または `Space` で確定する。
12. Table の実際の行順が変更されたことを確認する。
13. 移動した同じ行のハンドルへフォーカスが維持されていることを確認する。

#### このシナリオで固定する振る舞い

- 並べ替えモード開始時の初期フォーカス
- `Enter` / `Space` による開始と確定
- `ArrowUp` / `ArrowDown` による一行移動
- `Escape` によるキャンセル
- キャンセル時に行データを変更しないこと
- 確定時に実際の行データが変更されること
- DOM更新後も操作対象行のフォーカスを維持すること

### 4.4 Tab / Shift+Tab によるハンドル間フォーカス移動

#### 対象環境

- iframe
- non-iframe

#### テストデータ

`basicTable` を使用する。

#### 操作

1. 並べ替えモードをONにし、中間行のハンドルへフォーカスする。
2. `Tab` を押す。
3. 次の本文行のハンドルへフォーカスが移ることを確認する。
4. `Shift+Tab` を押す。
5. 元の本文行のハンドルへフォーカスが戻ることを確認する。

#### 検証方針

- `Tab` と `Shift+Tab` の両方向で、隣接する行ハンドルへ実際にフォーカスが移ることを代表ケースとして固定する。
- 先頭行からの `Shift+Tab`、末尾行からの `Tab`、すべての行位置などの境界パターンは網羅しない。
- 行インデックス計算や移動先決定の純粋ロジックは Jest へ任せ、Playwright ではブラウザ上の実フォーカスだけを確認する。

### 4.5 ポインターDnD主要フロー

#### 対象環境

- iframe
- non-iframe

#### テストデータ

`basicTable` を使用する。

#### 操作

1. 単純な Table を表示する。
2. 並べ替えモードをONにする。
3. 中間行のハンドルからドラッグを開始する。
4. 別の本文行へ移動する。
5. ドロップする。
6. Table の実際の行順が変更されたことを確認する。

#### 検証方針

最終的な行順を主要な期待値とする。

次の内部表現は原則として検証しない。

- DragOverlay のDOM構造
- 一時的な `is-dragging` class
- `transform` / `opacity` の具体値
- insertion indicator の内部状態
- dnd-kit の source / target オブジェクト

Playwright のドラッグ操作が環境依存で不安定になる場合は、固定waitや内部イベント注入で無理に成立させず、原因を報告する。

### 4.6 hoverによるハンドル表示・非表示

#### 対象環境

hover可能なデスクトップ環境を対象とする。

- iframe
- non-iframe

#### テストデータ

`basicTable` を使用し、次の2形態で同じシナリオを確認する。

- 通常幅
- 全幅

#### 各幅で確認する一連の操作

1. 明示的な並べ替えモードがOFFであることを前提とする。
2. Table 上へポインターを移動する。
3. 行ハンドルが表示されることを確認する。
4. Table からポインターを離す。
5. 行ハンドルが非表示になることを確認する。
6. 再び Table 上へポインターを移動する。
7. 行ハンドルが表示されることを確認する。
8. Table のセルをクリックし、セル編集へ移る。
9. 行ハンドルが非表示になることを確認する。

#### 全幅テーブルで追加確認すること

- ハンドルが画面外へ隠れず、利用者が操作可能な位置に表示されることを確認する。
- 厳密な座標値やCSS値ではなく、「表示され、操作可能である」という振る舞いを確認する。

#### 検証方針

- 通常幅 / 全幅のそれぞれについて、表示 → 離脱で非表示 → 再表示 → セル編集で非表示、を一つのシナリオとして固定する。
- hoverは明示的な並べ替えモードのON/OFFそのものとして扱わず、ドラッグ操作の入口としての既存仕様を確認する。
- hover状態を表す内部classやReact stateは主要な期待値にせず、利用者から見たハンドルの表示状態を確認する。
- タッチ端末のエミュレーションは #118 の必須範囲に含めない。

### 4.7 結合セル制約の代表フロー

#### 対象環境

まず iframe で代表ケースを確認する。

non-iframe へ同じケースを機械的に複製するのは、環境差による回帰が確認された場合に限る。基本的なポインターDnD自体は 4.5 で iframe / non-iframe の両方を確認する。

#### テストデータ

`mergedCellsTable` を使用する。

#### ケースA: `colspan` を越える安全な移動

1. 並べ替えモードをONにする。
2. `colspan` 行の前後にある通常行を使い、横結合行を越える位置へ移動する。
3. 移動を確定する。
4. Table の行順が期待どおり変更されることを確認する。

`colspan` が存在すること自体を理由に移動を拒否しないことを確認する。

#### ケースB: `rowspan` を分断する移動の拒否

1. 並べ替えモードをONにする。
2. 通常行を `rowspan` の結合範囲を分断する位置へ移動しようとする。
3. 移動が確定されないことを確認する。
4. Table の行順が操作前から変更されていないことを確認する。

主要な期待値は「許可 / 拒否」と「最終的な行順」とする。エラー通知の文言全文、一時class、挿入線の内部状態などは主要な期待値にしない。

### 4.8 長距離キーボード移動時のスクロール追従

#### 対象環境

まず iframe のみ1ケースとする。

non-iframe まで同じケースを複製するのは、環境差による回帰が実際に確認された場合に限る。

#### テストデータ

`longTable` を使用する。

#### 操作

1. 上部の行からキーボード並べ替えを開始する。
2. `ArrowDown` を複数回押して画面外の移動先へ進める。
3. 現在の移動先が viewport 内へ追従して表示されることを確認する。
4. 操作対象ハンドルのフォーカスが失われていないことを確認する。

#### 注意

座標やスクロール量の厳密値は確認しない。

「利用者が現在の移動先を確認でき、キーボード操作を継続できる」という振る舞いだけを固定する。

このケースがブラウザタイミングへ強く依存して安定しない場合は、本Issueで無理に残さず、原因と再現条件を報告する。

### 4.9 Undo / Redo と履歴単位

#### 対象環境

まず iframe で代表ケースを確認する。

non-iframe へ同じケースを機械的に複製するのは、Undo / Redo の結果に環境差が確認された場合に限る。基本的なポインターDnDとキーボード操作自体は、それぞれ 4.5 と 4.3 で iframe / non-iframe の両方を確認する。

#### テストデータ

`basicTable` を使用する。

#### ケースA: ポインターDnD後の Undo / Redo

1. 初期の行順を確認する。
2. ポインターDnDで一回だけ行を移動する。
3. 移動後の行順を確認する。
4. WordPress エディターの Undo を一回実行する。
5. 初期の行順へ戻ることを確認する。
6. Redo を一回実行する。
7. 移動後の行順が再適用されることを確認する。

#### ケースB: キーボード並べ替え後の Undo / Redo

1. 初期の行順を確認する。
2. キーボードで一回だけ行を移動して確定する。
3. 移動後の行順を確認する。
4. WordPress エディターの Undo を一回実行する。
5. 初期の行順へ戻ることを確認する。
6. Redo を一回実行する。
7. 移動後の行順が再適用されることを確認する。

#### ケースC: 2回の連続移動に対する履歴単位

1. 初期の行順を確認する。
2. 行移動Aを一回実行し、確定後の行順Aを確認する。
3. 行移動Bを一回実行し、確定後の行順Bを確認する。
4. Undo を一回実行し、行順Aへ戻ることを確認する。
5. Undo をもう一回実行し、初期の行順へ戻ることを確認する。
6. Redo を一回実行し、行順Aが再適用されることを確認する。
7. Redo をもう一回実行し、行順Bが再適用されることを確認する。

履歴単位の代表確認では、ポインターまたはキーボードのうち安定して再現できる一方の操作経路を使用する。ケースA・Bで両方の入力経路から履歴が作成されることは別途確認する。

#### 検証方針

- 「一回の確定した行移動が一回の Undo / Redo で戻る・再適用される」ことをユーザー可視の行順で確認する。
- 2回の連続移動では、一回の行移動が一つの履歴単位として扱われることを確認する。
- Undo / Redo の実行は、利用可能であれば `@wordpress/e2e-test-utils-playwright` の helper、またはエディターのユーザー向け操作を使用する。
- `@wordpress/data` の内部履歴、undo stack の長さ、内部 action 名などは主要な期待値にしない。
- 大量の連続移動、履歴上限、他ブロック編集との複雑な履歴混在までは #118 で網羅しない。

## 5. iframe / non-iframe のテスト範囲

| シナリオ | iframe | non-iframe |
|---|:---:|:---:|
| キーボード主要フロー | ✅ | ✅ |
| Tab / Shift+Tab フォーカス移動 | ✅ | ✅ |
| ポインターDnD主要フロー | ✅ | ✅ |
| hover: 通常幅 | ✅ | ✅ |
| hover: 全幅 | ✅ | ✅ |
| 結合セル制約の代表フロー | ✅ | 原則省略 |
| 長距離スクロール追従 | ✅ | 原則省略 |
| Undo / Redo・履歴単位 | ✅ | 原則省略 |

同じ振る舞いを確認するだけのケースを無目的に増やさない。ただし hover は iframe / non-iframe と通常幅 / 全幅の組み合わせが実際のDOM配置・表示領域に影響するため、両環境・両幅で代表シナリオを確認する。

## 6. セレクター方針

セレクターは次の優先順位で選ぶ。

1. role と accessible name
2. Table 内に表示される行内容
3. `@wordpress/e2e-test-utils-playwright` の helper
4. 安定した公開DOMが必要な場合のみ限定的な selector

次のような内部実装依存を、主要な期待値やテスト操作の中心にしない。

- `.is-keyboard-reordering`
- `.is-dragging`
- `data-table-reorder-row-id`
- React内部state
- 一時的な inline style
- dnd-kit 固有の内部DOM

ハンドルを識別する必要がある場合は、まず button role と accessible name を利用する。

## 7. #117 Jest テストとの境界

次の内容は原則として Playwright で細かく再検証せず、#117 の Jest テストへ任せる。

- keyboard reorder の細かな状態遷移
- Tab / Shift+Tab の移動先インデックス計算と境界条件
- insertion index の計算
- 先頭 / 末尾判定
- rowspan range の計算
- non-movable row の算出
- drag session の候補計算
- commit / cancel の純粋ロジック
- drag visuals の内部計算

Playwright では、それらを組み合わせた最終的なユーザー操作がブラウザ上で成立することだけを確認する。

`mergedCellsTable` を用いるE2Eでも `rowspan` 制約を網羅せず、「`colspan` は安全な移動を妨げない」「`rowspan` を分断する移動は拒否される」という代表的な統合結果だけを固定する。

Undo / Redo では内部の履歴実装を検証せず、ポインターとキーボードの両経路で履歴が作られること、および一回の確定した行移動が一つの履歴単位として扱われることだけを実ブラウザで固定する。

## 8. 本Issueで追加しないテスト

次は #118 の必須範囲から外す。

- Tab / Shift+Tab の先頭・末尾を含む全境界パターン
- 先頭・末尾での並べ替え境界の全パターン
- rowspan 制約の全パターン
- `colspan` / `rowspan` の組み合わせ網羅
- `thead` / `tfoot` の網羅ケース
- Undo / Redo の大量連続操作、履歴上限、他ブロック編集との複雑な履歴混在
- instruction UI のCSS値
- ARIA live region の文言全文一致
- DragOverlay の見た目
- insertion indicator の表示位置詳細
- full-width のCSS値・座標値の詳細検証
- hover開始・終了タイミングの内部状態網羅
- タッチ端末のhoverエミュレーション
- セル編集復帰の全パターン
- reload直後のフォーカス特殊ケース
- Gutenberg内部DOM構造そのものの検証

## 10. 不具合を発見した場合

テストを通すために本体実装の仕様変更を行わない。

本Issueの目的は、現在の仕様に沿った主要な振る舞いを Playwright で固定することである。

実装中に次のいずれかを発見した場合は、期待値を都合よく変更したり本体を修正したりせず、再現条件と観測結果を報告する。

- 要件と現在の実装が一致していない
- iframe と non-iframe で振る舞いが異なる
- 通常幅と全幅でhover挙動が異なる
- Undo / Redo の履歴単位が一回の確定した行移動と一致しない
- 現在の実装に既存不具合がある
- Playwright から安定して操作できないブラウザ依存がある
- テストを成立させるために本体修正が必要になる

必要であれば別Issueとして切り出し、#118 のスコープを膨らませない。
