## Goal

現在の `main` に実装済みの Table Reorder の振る舞いを基準に、要件定義書と基本設計書を現在の製品仕様へ同期するための更新方針を確定する。

このIssueでは文書そのものは更新せず、現状との差分、文書ごとの責務、更新対象、更新順序を計画として整理する。

文書更新では、次の3層を明確に分ける。

1. **要件定義書: What**
   - 利用者に何を提供するか。
   - 何ができる必要があるか。
   - どのような制約を満たす必要があるか。
2. **基本設計書: How**
   - 要件を、利用者から見てどのような画面・操作・状態・情報提供で実現するか。
3. **実装プラン・プログラム: Technical How**
   - プログラムとしてどのように実装するか。

要件定義書と基本設計書は、プログラムの知識を前提としない経営者層でも内容を理解できる粒度で記述する。

## Documentation principles

### 要件定義書

要件定義書には **What** を記述する。

記述する内容:

- 対象となる利用者や機能の範囲。
- 利用者ができる必要があること。
- 機能として保証する振る舞い。
- 利用上の制約や例外。
- アクセシビリティ上満たす必要がある性質。

記述しない内容:

- 具体的な実現方法。
- 画面や操作の詳細な流れ。
- プログラム内部の構造。
- ファイル名、関数名、クラス名、イベント名、内部状態名。
- DOM、API、ライブラリ設定、CSSなどの実装詳細。

### 基本設計書

基本設計書には **How** を記述する。

ただし、ここでいう How は **利用者から見た実現方法** とする。

記述する内容:

- どの画面・操作入口を利用するか。
- どのような操作手順で目的を達成するか。
- 操作中にどのような状態や案内を見せるか。
- 確定、キャンセル、エラー時にどのように振る舞うか。
- フォーカスや支援技術への情報提供をどのように行うか。
- PC、タッチ、キーボードなど入力方法ごとの利用者向けの違い。

記述しない内容:

- プログラム内部の構造や責務分割。
- ファイル名、関数名、クラス名、hook、controllerなどの実装要素。
- DOMの探索方法やイベント登録方法。
- ライブラリの設定値。
- CSS selectorや具体的なプログラム処理。

### 実装との関係

現在の `main` は文書更新の事実確認に利用する。

ただし、実装上の仕組みをそのまま要件定義書・基本設計書へ転記しない。

実装を確認して得た事実は、次のように利用者向けの表現へ変換する。

- 内部処理の説明ではなく、利用者が何をできるかへ変換する。
- 内部状態の説明ではなく、利用者から見える状態へ変換する。
- プログラム上の制約ではなく、利用上の制約へ変換する。

## Current state and gaps

### 1. 対応するTableブロック

現在の製品は、WordPress Core Table と Flexible Table Block の両方を対象としている。

一方、既存の要件定義書・アクセシビリティ要件定義書・アクセシビリティ基本設計書には、Core Tableのみを対象として読める記述が残っている。

更新時は、Table Reorderが対応するTableブロック全体を対象として表現し、ブロックごとの内部的な違いは要件定義書・基本設計書へ持ち込まない。

### 2. 通常操作の基本設計

現在は通常操作の基本設計書が存在せず、アクセシビリティ基本設計書の中にPCやタッチの通常操作まで含まれている。

このため、基本要件をどのような利用者向け操作で実現するかを説明する通常操作の基本設計書を新設する。

通常操作の基本設計では、主に次を扱う。

- PCでの行ハンドルの表示とドラッグ操作。
- タッチ端末での行並べ替え操作への切り替え。
- PC・タッチでドラッグを使わず移動先を選ぶ操作。
- 移動可能な行と移動できない行の見せ方。
- 移動先の表示。
- 確定とキャンセル。
- 操作中のスクロール。
- iframe / non-iframeでも同じ意味の操作を提供すること。

### 3. PC・タッチ・キーボードの操作

現在の製品では、入力方法に応じて複数の操作方法を提供している。

文書更新では、次の境界を明確にする。

- 「どの操作方法を提供する必要があるか」は要件定義書で扱う。
- 「各操作方法をどのような手順で利用するか」は基本設計書で扱う。

キーボード操作についても、キー入力を処理する内部方式ではなく、利用者が開始、移動、確定、キャンセルをどのように行うかを記述する。

### 4. 結合セルの制約

現在の製品では、縦に結合されたセルを壊さないように行移動を制限しつつ、結合範囲外の行は結合範囲全体を越えて移動できる。

要件定義書では、次の **制約そのもの** を扱う。

- 縦に結合されたセルの範囲内の行は移動できない。
- 結合範囲の途中へ別の行を挿入できない。
- 結合範囲外の行は、結合範囲全体を越えて前後へ移動できる。
- 横方向の結合だけを含む行は、安全に行単位で移動できる場合は移動できる。

基本設計書では、この制約を利用者にどのように示し、移動できない操作をどのように扱うかを記述する。

### 5. 操作案内と初回案内

現在の製品では、操作方法や操作中の状態に応じて画面上の案内を提供している。また、キーボード利用時とタッチ利用時には初回の機能発見を補助する案内がある。

既存のアクセシビリティ基本設計書には、現在の画面表示と一致しない古い文言が残っている。

更新時は、次を整理する。

- 要件定義書では「必要な操作案内を画面上で確認できること」を定義する。
- 基本設計書では「いつ、どのような目的の案内を表示するか」を定義する。
- 具体的な文言を正本として管理する必要がある場合も、利用者向けの文言として記載し、プログラム上の識別子は記載しない。

### 6. フォーカスと操作文脈

現在の製品では、キーボード操作で行並べ替えへ入った後も、利用者が操作対象を見失わないことを重視している。

要件定義書では、次の **必要な性質** を扱う。

- キーボードだけで目的の操作へ到達できる。
- 操作中・操作後に対象を見失わない。
- フォーカスされている操作対象を視覚的に確認できる。
- Table Reorder自身の表示によってフォーカス対象が完全に隠れない。

基本設計書では、どの入口から行の操作へ移り、操作中・確定後・キャンセル後にどこへ操作位置を保つかを説明する。

### 7. 支援技術への情報提供

現在の製品では、操作対象、操作状態、移動結果、移動できない理由を支援技術へ伝える。

要件定義書では、これらの情報を確認できる必要があることを定義する。

基本設計書では、どの場面でどのような情報を伝えるかを利用者視点で整理する。

具体的なARIA属性や通知処理の実装方法は記載しない。

### 8. iframe / non-iframe

iframe / non-iframeの両方で同じ意味の操作を提供する要件は、既存文書にも存在する。

更新時は新しい仕様として追加するのではなく、現在の対応範囲と矛盾しない表現へ揃える。

## Document responsibility after update

### Basic requirements

`table-reorder-requirements.md` は、Table Reorderとして **何を提供するか** を定義する。

主な責務:

- 対応するTableブロックの範囲。
- 本文行を並べ替えられること。
- PCとタッチで利用できる通常の操作方法。
- データを保持すること。
- 有効な移動だけを確定すること。
- 一回の行移動を一回のUndoで戻せること。
- 縦結合・横結合を含む行移動の制約。
- iframe / non-iframeで同じ基本要件を満たすこと。

画面構成、操作手順、具体的な実現方法は記述しない。

### Accessibility requirements

`table-reorder-accessibility-requirements.md` は、Table Reorderとして **アクセシビリティ上何を満たす必要があるか** を定義する。

主な責務:

- キーボードだけで並べ替えを完了できること。
- ドラッグを必要としない単一ポインター操作で並べ替えを完了できること。
- 操作対象へ論理的な順序で到達できること。
- フォーカスを確認でき、操作対象を見失わないこと。
- 操作UIを細かく狙わなくても操作できること。
- 必要な操作案内を画面上で確認できること。
- 操作対象、状態、結果、移動できない理由を支援技術から確認できること。
- 基本要件の移動制約をアクセシビリティ操作にも適用すること。

通常操作の要件を重複して定義しない。

### Normal interaction design

新設する通常操作の基本設計書は、基本要件を **利用者がどのように操作して実現するか** を定義する。

主な責務:

- PCでの行ハンドルの見つけ方とドラッグ操作。
- タッチ端末での行並べ替え操作への切り替え。
- PC・タッチでドラッグを使わず移動先を選択する操作。
- 移動先の見せ方。
- 確定とキャンセルの流れ。
- 移動できない行・位置の扱い。
- 操作中の案内とスクロール。
- iframe / non-iframeで同じ意味の操作を維持すること。

アクセシビリティ固有の要件やフォーカス・支援技術に関する設計はアクセシビリティ基本設計へ委ねる。

### Accessibility design

`table-reorder-accessibility-design.md` は、アクセシビリティ要件を **利用者向けの操作・状態・情報提供としてどのように実現するか** を定義する。

主な責務:

- キーボード利用者が行の並べ替え操作へ入る方法。
- キーボードでの開始、移動、確定、キャンセル。
- 操作前・操作中・操作後のフォーカスの扱い。
- フォーカスの視認性と遮蔽防止。
- ポインター操作UIの操作しやすい大きさ。
- 初回の機能発見を補助する案内。
- 操作中の画面案内。
- 操作対象を識別するための情報。
- 操作状態、結果、移動できない理由の支援技術への情報提供。

通常操作の基本設計を参照し、通常操作そのものを重複して再定義しない。

## Issue breakdown

プランレビュー後、文書更新は次の3単位を基本とする。

- [ ] 基本要件・アクセシビリティ要件を現在の仕様へ同期する。
- [ ] 通常操作の基本設計書を新設する。
- [ ] アクセシビリティ基本設計を現在の仕様と文書責務へ同期する。

別Issueへさらに分割するのは、更新範囲が独立してレビューすべき規模へ広がった場合だけとする。

## Validation

このIssueは計画書のみを変更するため、検証は文書差分の確認に限定する。

- `git diff --check origin/main...HEAD`
  - Expected: whitespace errorがない。

後続の文書更新では、各文書について少なくとも次をレビューする。

- 要件定義書が What に留まっている。
- 基本設計書が利用者視点の How に留まっている。
- プログラムレベルの説明が混入していない。
- 経営者層がプログラム知識なしで理解できる。
- 現在の `main` の利用者向け振る舞いと矛盾していない。
- 文書間で同じ内容を必要以上に重複管理していない。

## Completion criteria

- 要件定義書 = What、基本設計書 = 非技術的な How、実装プラン・プログラム = Technical How の境界が明文化されている。
- 要件定義書・基本設計書を経営者層が読める粒度とする方針が明文化されている。
- プログラムレベルの内容を要件定義書・基本設計書へ記載しない方針が明文化されている。
- 現在の `main` と既存3文書の主要な差分が利用者向けの観点で整理されている。
- 通常操作の基本設計書を新設する方針が整理されている。
- 基本要件、アクセシビリティ要件、通常操作基本設計、アクセシビリティ基本設計の責務が区別されている。
- 後続の文書更新を3単位へ分割できる。
- このIssueでは要件定義書・基本設計書・製品コードを変更していない。

## Notes

- 現在の `main` は仕様確認の根拠として使用するが、プログラム構造そのものを文書仕様にはしない。
- 現行実装に文書化されていない振る舞いが見つかった場合は、まず利用者向け仕様として確定済みかを確認する。単に実装されているという理由だけで要件や基本設計へ昇格させない。
- 文書を詳しくすること自体を目的にせず、現在の製品仕様を正確に伝えるために必要十分な内容へ留める。
