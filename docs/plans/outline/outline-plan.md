# PLAN-016: Yamabiko Outline

## References

- Parent issue: #16
- Requirements: `../requirements/yamabiko-outline-requirements.md`
- Design: `../design/yamabiko-outline-high-level-design.md`

## Goal

Yamabiko Outline の要件定義書と基本設計書に基づき、技術検証から MVP 完成までを、レビュー可能な単位で段階的に実装できる状態にする。

この計画では、実装範囲、主要モジュール、実装フェーズ、テスト方針、実装前の判断事項、実装中に検証する事項、および子 Issue の分割方針を定める。

## Scope

### Included

- 投稿および固定ページのブロックエディターに追加する独立した文書構造サイドバー
- `core/heading` と innerBlocks 内の `core/heading` からのアウトライン生成
- `core/accordion-heading`、`core/html`、`core/freeform`、テスト用カスタムブロックへの対応
- 1ブロック内の複数見出し
- 見出し構造の診断
- アウトライン項目から元ブロックへの移動
- 未対応または解析失敗による不完全なアウトラインの通知
- キーボード操作と状態表示に必要なアクセシビリティ対応
- 単体テスト、結合テスト、E2E テスト

### Not included

- Gutenberg 標準の Document Outline の直接変更
- ページ全体のブロック構造を表示する Structure View
- ドラッグ＆ドロップ、複製、削除などの構造編集
- 見出しレベルなどの自動修正
- サイトエディター、ウィジェットエディター、カスタム投稿タイプへの対応
- PHP の `render_callback` やショートコードを実行した解析
- 公開アダプター API と PHP-only ブロック向け公開仕様の製品化
- ToC ブロックや AI 機能との統合

## Approach

- WordPress Data Store のブロック状態を単一の正とする。
- ブロックツリーを文書順に走査し、各ブロックを1つの Resolver、Adapter、または Parser に割り当てる。
- 処理優先順位は、組み込み Resolver、登録済み Adapter、HTML Heading Parser の順とする。
- 取得した見出しは共通の `OutlineNode` へ変換する。
- 取得できない情報は推測せず、不完全な可能性として通知する。
- 表示、解析、診断、ナビゲーションの責務を分離する。
- 1つの処理やアダプターの失敗で、取得済みのアウトライン全体を失わない。
- 各フェーズでレビュー可能な成果を作り、次のフェーズへ進む前に結果を確認する。

## Architecture

### Document Outline Sidebar

アウトライン、診断結果、不完全なアウトラインの通知を表示する。クリックとキーボード操作を Block Navigator へ渡す。

### Block Tree Selector

WordPress Data Store から現在のブロックツリーを取得し、ブロック変更に応じて最新状態を提供する。

### Standard Heading Resolver

`core/heading` と innerBlocks 内の `core/heading` を `OutlineNode` へ変換する。

### Outline Adapter Registry

ブロック名をキーに内部アダプターを管理し、重複登録、不正な返却値、例外を局所化する。

### HTML Heading Parser

`core/html` と `core/freeform` の保存済み静的 HTML から H1 から H6 のみを抽出する。スクリプト、ショートコード、PHP、動的レンダリングは実行しない。

### Outline Diagnostics

H1 の複数使用、見出しレベルの飛び、空見出し、見出しなし、同一階層の重複見出しを診断する。

### Block Navigator

対象ブロックの存在と移動可否を確認し、親の展開、ブロック選択、スクロール、可能な場合のフォーカスを行う。

## Implementation phases

### Phase 1: 技術検証

- Outcome:
  - 投稿および固定ページでプラグインサイドバーを表示できる。
  - Data Store からブロックツリーを取得できる。
  - 標準 Heading と innerBlocks 内 Heading を文書順に表示できる。
  - アウトライン項目から元ブロックを選択できる。
- Tasks:
  - サイドバーの登録方式を確認する。
  - Block Tree Selector と Standard Heading Resolver の最小構成を作る。
  - `OutlineNode` の内部型と一意な ID の生成方針を定める。
  - 最小の内部アダプター登録方式を検証する。
  - 100ブロック程度の投稿で更新処理を計測する。
- Validation:
  - 投稿と固定ページでのみサイドバーが表示される。
  - 見出しの順序、レベル、テキストが正しい。
  - 見出し選択で元ブロックへ到達できる。
  - ブロック編集を妨げる明確な入力遅延がない。

### Phase 2: アウトライン生成基盤

- Outcome:
  - Resolver、Registry、Parser を通して対応ブロックを重複なく処理できる。
  - 1ブロック内の複数見出しを表現できる。
- Tasks:
  - Outline Adapter Registry を実装する。
  - `core/accordion-heading` 用の組み込み処理を追加する。
  - HTML Heading Parser を実装する。
  - テスト用カスタムブロックと内部アダプターを追加する。
  - 不正な返却値とアダプター例外を隔離する。
- Validation:
  - 各ブロックが1つの処理経路だけで扱われる。
  - HTML と Classic ブロックの静的な H1 から H6 が抽出される。
  - スクリプト、ショートコード、PHP、動的レンダリングが実行されない。
  - 複数見出しの順序と一意な ID が維持される。

### Phase 3: 診断と不完全通知

- Outcome:
  - 基本的な見出し構造の問題を表示できる。
  - 取得できない可能性を隠さず通知できる。
- Tasks:
  - Outline Diagnostics を実装する。
  - 診断レベルと対象ブロックへの関連付けを追加する。
  - 未対応ブロック、解析失敗、アダプター失敗を集約する。
  - 取得済みアウトラインを維持したまま不完全通知を表示する。
- Validation:
  - H1 重複、階層飛び、空見出し、見出しなし、同一階層の重複を判定できる。
  - 自動修正を行わない。
  - 1つの解析失敗でほかの見出しや診断が消えない。

### Phase 4: ナビゲーションとアクセシビリティ

- Outcome:
  - アウトラインから対象ブロックへ安定して移動できる。
  - キーボードで主要操作を完了できる。
- Tasks:
  - Block Navigator を実装する。
  - 必要に応じた親ブロックの展開、選択、スクロールを実装する。
  - 可能な場合のみ見出し編集部分へフォーカスする。
  - 移動不能理由を表示する。
  - 警告や状態を色だけに依存せず表現する。
- Validation:
  - クリックと Enter キーで対象ブロックへ移動できる。
  - 個別見出しへ移動できないカスタムブロックでも元ブロックを選択できる。
  - 削除済みまたは移動不能な対象で安全に中止できる。
  - フォーカス位置を視覚的に確認できる。

### Phase 5: MVP 統合と E2E 検証

- Outcome:
  - 要件定義書の MVP 受け入れ条件を一連の操作として確認できる。
- Tasks:
  - 各モジュールをサイドバーへ統合する。
  - 同期パターンを安全に取得できる範囲で検証する。
  - 単体、結合、E2E テストを整備する。
  - プラグイン停止後に投稿内容へ影響しないことを確認する。
  - 実測に基づいて必要最小限の性能改善を行う。
- Validation:
  - 対応見出しを文書順に表示できる。
  - 見出し選択、診断、不完全通知、キーボード操作が連携して動作する。
  - 未対応ブロックや解析失敗があっても画面全体が停止しない。
  - 投稿内容とフロントエンド出力を変更しない。

## Decisions and validation questions

### Decide before implementation

- プラグインサイドバーの具体的な登録方式と対象エディターの判定方法
- `OutlineNode.id` の安定性と、1ブロック内の複数見出しを識別する規則
- Accordion の見出しテキストとレベルを取得する正式な属性
- 内部アダプターの最小インターフェースと入力・出力の検証規則
- 未対応ブロックとして通知する対象を、誤検知を増やさず判定する最小条件

### Validate during implementation

- Data Store の選択だけで十分に対象位置へスクロールできるか
- 折りたたまれた親ブロックを公開 API で展開できるか
- HTML と Classic ブロックを安全かつ期待どおり解析できるか
- 同期パターン内の見出しを展開済みブロックツリーから安定して取得できるか
- 1ブロック内の複数見出しへ個別に移動できるか
- 100ブロック程度の投稿で実用的な応答性を維持できるか
- 未対応ブロック判定が利用者を過度に不安にさせない精度になるか

## Issue breakdown

プランのレビュー後、次の単位を子 Issue として作成する。

- [ ] 技術検証と最小サイドバーを実装する
- [ ] アウトライン生成基盤と内部アダプターを実装する
- [ ] 見出し診断と不完全なアウトライン通知を実装する
- [ ] ブロックナビゲーションとアクセシビリティを実装する
- [ ] MVP を統合して E2E 検証を行う

子 Issue には、対応フェーズ、参照文書、完了条件、検証方法、非対象を記載する。

## Validation

実装時の具体的なコマンドは `docs/development/testing.md` を正とし、各子 Issue で変更内容に応じた検証を選択する。

最低限、次を確認する。

- TypeScript と JavaScript の静的検査
- 対象モジュールの単体テスト
- ブロックエディター上の結合または E2E テスト
- 投稿および固定ページでの手動確認
- 100ブロック程度の投稿を使った応答性の確認
- プラグイン停止後の投稿内容とフロントエンド表示の確認

## Completion criteria

- 技術検証と MVP の範囲が区別されている。
- 主要モジュールと責務が定義されている。
- 実装フェーズごとの成果、作業、検証内容が明確である。
- 実装前に決める事項と、実装中に検証する事項が分離されている。
- レビュー後に子 Issue を作成できる粒度で分割案が示されている。
- 要件定義書と基本設計書の MVP 範囲、非対象、設計原則に矛盾しない。

## Notes

- Issue #16 では実装を行わない。
- 公開アダプター API と PHP-only ブロック向け公開仕様は、内部 API を複数のブロックで検証した後の製品化フェーズで扱う。
- 技術検証で基本設計の前提が成立しない場合は、回避実装を先に追加せず、要件定義書、基本設計書、この計画の順で影響を整理する。
